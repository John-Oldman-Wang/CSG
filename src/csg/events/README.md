# events — 事件驱动层

## 做什么

把数据变化转换成**待人处理的任务**，而不是交易信号。

```
量化系统：事件 → 信号 → 自动下单
CSG     ：事件 → 任务（材料+问题）→ 人判断 → 结论落库
```

```
detector.py     扫描数据产生事件（幂等去重）
strategies.py   事件 → 复核任务（含 SLA 与必答问题）
```

## 怎么做

### 事件必须幂等去重

`event_id = hash(event_type, code, ref_date, ref_key)`。

MacBook 休眠唤醒后补跑扫描是常态，重复事件会淹没提醒，
进而导致用户静音渠道——**那等于整套系统失效**。

### 过滤比触发更重要

默认只对 watchlist（观察池 + 持仓）产生任务。对不关心的股票发提醒，
是最快的自我失效路径。

### 任务携带三样东西

1. **当初写下的证伪条件** —— 监控的对象是假设，不是价格
2. **系统备好的材料** —— 超额跌幅拆分、财务快照、期间事件
3. **必答问题** —— 含「以今天的价格和信息，我会重新买入吗？」

最后一问用于切断沉没成本：把「我亏了 20% 要不要割」重构为
「这是不是我今天愿意持有的资产」。

### SLA 存在的意义

混合派把「下跌怎么办」交给人的判断，其最大失效风险不是逻辑漏洞
而是**执行**——任务积压不处理。`due_at` 与状态机直接喂给复盘层的
「及时处理率」统计。

## 已关闭的事件（验证驱动）

`research_downgrade` 由 P1 降为 P2 且不再生成任务。原设计依据
「分析师不愿得罪覆盖对象，敢下调说明问题明确」的先验推理，
被验证④ 证伪：

```
发现期  下调超额60日 +1.62%、250日 +8.09%
验证期  下调超额60日 −3.00%、250日 −10.72%
```

符号完全反转，是噪音的典型特征。**若只看发现期就接入，
等于连续数年向用户推送噪音。**
